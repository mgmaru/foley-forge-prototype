# LLMアプリケーションにおける観測ポイント・評価ポイント設計方針

## 1. 目的

本ドキュメントは、LLMを利用するアプリケーションにおいて、生成品質の低下箇所を特定しやすくするための設計方針を定義する。

LLMは確率的に出力が変動するため、通常のソフトウェアと比べて、最終出力だけを確認しても品質低下の原因を特定しにくい。

特に、LLMを多段に利用する構成では、どの工程で品質が落ちたのかを切り分けるために、各工程の入出力を記録し、必要な地点で品質評価を行う必要がある。

---

## 2. 用語定義

### 2.1 観測ポイント

観測ポイントとは、LLMパイプラインの途中状態を記録・確認できるようにする地点である。

主な目的は、後から処理内容を追跡し、品質低下や不具合の原因を調査できるようにすることである。

観測ポイントでは、以下のような情報を記録する。

| 項目 | 内容 |
|---|---|
| 入力 | ユーザー入力、前工程から渡されたデータ |
| プロンプト | LLMに渡した最終的なプロンプト |
| モデル設定 | モデル名、temperature、top_pなど |
| LLM出力 | LLMから返された生の出力 |
| 後処理結果 | JSON変換、整形、抽出後のデータ |
| 処理情報 | token数、処理時間、retry回数 |
| エラー情報 | パースエラー、APIエラー、バリデーションエラー |

観測ポイントは、品質を直接判定する地点とは限らない。

---

### 2.2 評価ポイント

評価ポイントとは、観測された入力・出力・中間データに対して、品質や妥当性を判定する地点である。

主な目的は、その工程の出力を次工程に渡してよいかを判断することである。

評価ポイントでは、以下のような観点で判定を行う。

| 評価観点 | 内容 |
|---|---|
| 形式妥当性 | JSON形式、Markdown形式、指定スキーマなどを満たしているか |
| 制約充足性 | 指示された条件・制約を守っているか |
| 情報欠落 | 必要な情報が抜けていないか |
| 一貫性 | 前工程の内容と矛盾していないか |
| 目的適合性 | ユーザーの目的に沿った出力になっているか |
| 次工程適性 | 次の処理に渡せる品質か |

評価ポイントは、品質ゲートとして機能する。

---

### 2.3 品質ゲート

品質ゲートとは、ある工程の出力を次工程へ進めるかどうかを判断するための判定条件である。

評価ポイントで品質ゲートを満たさない場合、以下のような対応を行う。

| 対応 | 内容 |
|---|---|
| リトライ | 同一工程を再実行する |
| 補正 | 出力形式や不足情報を補正する |
| 前工程へ戻す | 入力やプロンプトを再生成する |
| 人間レビュー | 自動判定が難しい場合に人間へ確認を回す |
| エラー終了 | 継続困難な場合に処理を停止する |

---

## 3. 観測ポイントと評価ポイントの関係

観測ポイントと評価ポイントは、必ずしも同一ではない。

基本的な関係は以下のとおりである。

```text
観測ポイント：何が起きたかを記録する地点
評価ポイント：記録された内容をもとに良し悪しを判定する地点
```

評価を行うためには、原則として観測が必要である。  
そのため、評価ポイントは観測ポイントを兼ねることが多い。

一方で、すべての観測ポイントで評価を行う必要はない。

```text
観測ポイント ⊇ 評価ポイント
```

実装方針としては、観測ポイントは広めに配置し、評価ポイントは品質に影響する重要な境界に絞って配置する。

---

## 4. 基本方針

LLMアプリケーションでは、以下の方針で観測ポイントと評価ポイントを設計する。

1. 各LLMステップの入力・プロンプト・出力を観測する
2. 品質劣化が起きやすい工程の後に評価ポイントを置く
3. 評価に失敗した場合の分岐処理を定義する
4. 評価結果もログとして保存する
5. 最終出力だけでなく、中間生成物も確認できるようにする

---

## 5. 多段LLMパイプラインでの配置例

```text
[ユーザー入力]
   ↓
[Step 1: 意図分類]
   ├─ 観測：入力、プロンプト、LLM出力、分類結果
   └─ 評価：分類結果が妥当か
   ↓
[Step 2: 要件抽出]
   ├─ 観測：入力、プロンプト、LLM出力、抽出結果
   └─ 評価：必要な要件が欠落していないか
   ↓
[Step 3: 生成方針作成]
   ├─ 観測：入力、プロンプト、LLM出力、方針データ
   └─ 評価：制約を満たした方針になっているか
   ↓
[Step 4: 最終生成]
   ├─ 観測：入力、プロンプト、LLM出力、後処理結果
   └─ 評価：ユーザー目的を満たしているか
```

---

## 6. 観測対象

各LLMステップでは、最低限以下を観測対象とする。

| 分類 | 記録対象 |
|---|---|
| 入力情報 | ユーザー入力、前工程の出力 |
| プロンプト情報 | system prompt、user prompt、テンプレート変数 |
| モデル情報 | モデル名、temperature、top_p、max_tokens |
| 出力情報 | LLM生出力、整形後出力、構造化データ |
| 実行情報 | 実行時刻、処理時間、token数、retry回数 |
| エラー情報 | パースエラー、検証エラー、APIエラー |

---

## 7. 評価対象

評価ポイントでは、工程の目的に応じて評価対象を定義する。

| 工程 | 主な評価対象 |
|---|---|
| 意図分類 | 分類ラベルがユーザー入力と一致しているか |
| 要件抽出 | 必須要件・制約・前提条件が抜けていないか |
| 情報整理 | 重要情報が落ちていないか、矛盾がないか |
| 生成方針作成 | 出力方針が目的・制約に合っているか |
| 最終生成 | 最終成果物がユーザー目的を満たしているか |
| 後処理 | 出力形式・スキーマ・保存形式が正しいか |

---

## 8. 評価失敗時の扱い

評価ポイントで品質基準を満たさない場合、以下のいずれかの対応を行う。

| 条件 | 対応 |
|---|---|
| 出力形式のみ不正 | 後処理または再整形を行う |
| 情報が一部不足 | 不足情報を補完するために再生成する |
| 前工程の解釈が誤っている | 前工程に戻して再実行する |
| 判断が難しい | 人間レビューに回す |
| 継続不能 | エラーとして処理を停止する |

---

## 9. 実装時の注意点

### 9.1 最終出力だけを評価しない

多段LLM構成では、最終出力だけを評価しても原因の切り分けが難しい。  
各工程の中間出力を観測し、必要な地点で評価する。

### 9.2 すべての観測ポイントで評価しない

すべての観測ポイントで評価を行うと、コスト・レイテンシ・実装複雑度が増加する。  
評価ポイントは、品質劣化が発生しやすい重要な境界に絞る。

### 9.3 評価結果も記録する

評価ポイントでは、判定結果だけでなく、評価理由も記録する。

例：

```json
{
  "step": "requirements_extraction",
  "status": "failed",
  "reason": "必須項目である対象ユーザーが抽出されていない",
  "action": "retry"
}
```

### 9.4 再現性を確保する

品質問題を後から調査できるように、以下の情報を記録する。

- 入力
- プロンプト
- モデル名
- モデル設定
- LLM出力
- 後処理結果
- 評価結果
- 実行時刻

---

## 10. 推奨する設計方針

本アプリケーションでは、以下の方針を採用する。

```text
観測ポイントは広く配置する。
評価ポイントは重要な工程境界に絞って配置する。
評価に失敗した場合の分岐処理を明確にする。
評価結果もログとして保存する。
```

これにより、LLMの出力品質が低下した場合に、どの工程の入力・プロンプト・出力・後処理が原因であるかを切り分けやすくする。
