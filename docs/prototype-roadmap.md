## 0. 狙いと North Star

設計が固まった FoleyForge を**一気に作らず段階的に**作るための順序を定める。各段階は「作る対象」ではなく「**確認したい問い**」で区切る——作って終わりではなく、**仮説を検証して次へ**進むため。

> **North Star：プロトタイプの完成＝「改善ループ（外ループ）が1周回る」こと。**

design philosophy「まず生成アルゴリズムを確立 → GPU最適化は後」を具体化すると、ゴールは「**ログ→分析→改善→採用率で効果測定**が回り出すこと」。この一点で全段階の優先順位が決まる:

- **Phase 0–3** … ループを回すための**足場**
- **Phase 4** … ループが閉じる＝**プロトタイプのゴール（本丸）**
- **Phase 5–6** … ループが回り始めてからの仕事（**プロトタイプ後**。dev §2.2 後期・[FF-D008](./decisions.md)）

### このロードマップの背骨（4原則）

1. **リスク先行**：存在的リスク（モデル実現性）から順に、最も安く「怖い未知」を潰す。
2. **縦スライス優先**：薄くても end-to-end を先に通す。横に全 Step を作り込まない。
3. **各フェーズは「問いに答える」単位**：仮説検証で次へ。NG なら早く軌道修正。
4. **scope を切る**：各フェーズで「やらないこと」を明示し、スコープ膨張を防ぐ。

## 2. 各フェーズの詳細

### Phase 0 — モデル実現性スパイク（アプリ外）

- **問い**：
  - 選んだ T2A（Stable Audio Open 等）は、手書きプロンプトで「アニメ寄りSE」を実用レベルで作れるか？
  - ローカルGPUでの生成時間・VRAM は許容内か？
  - CFG のスイートスポットはどこか？
- **作る範囲**：最小スクリプト/ノートブックで、手書きプロンプト数本 × CFG 数点を生成して耳で確認（モデル候補を1–2比較）。
- **完了条件**：「このモデルでいける」or「モデルを変える」の判断＋生成1本あたりの**時間・VRAM 実測値**。
- **範囲外**：アプリ化／LLM／構造化データ／評価指標／UI（すべて後）。
- **なぜここ**：「No」なら前提が崩れる、最も安く早く潰すべき**存在的リスク**だから。「まず生成アルゴリズムを確立」の第一歩。

### Phase 1 — 薄い縦スライス（end-to-end が1本通る）

- **問い**：
  - 「入力→構造化→プロンプト→生成→提示」の鎖は通るか？
  - 構造化データ経由のプロンプトは、素のプロンプトより筋の良い音を生むか（augmentation 仮説の初検証）？
- **作る範囲**：Step1（最小入力）→ Step2（LLM・**スキーマ最小**）→ Step3（決定論ビルダー・**まず1戦略**）→ Step5（diffusers 直叩き・Best-of-1〜少数）→ Step8（音を返すだけ）。UI は最小（CLI でも可）。
- **完了条件**：シーン記述→音1本、自分の耳で「素のプロンプトよりマシ」と言える（スキーマ v0 が回る）。
- **範囲外**：
  - 3戦略フル／CLAP・PQ採点／配分・abstain
  - ログ基盤／層Aゲート
  - パーソナライズ／GPU最適化
- **なぜここ**：採点も人間ラベルも「提示する候補」が無いと無意味。**まず鎖を通す**（[FF-D010](./decisions.md)：Step2 の豊かなスキーマとセットで効く）。

### Phase 2 — 改善ループの三点セット＋多様性

- **問い**：
  - 改善に必要なデータを毎セッション捕捉できるか？
  - 多様性（3戦略＋Best-of-N）はユーザの「選ぶ」を意味あるものにするか？
- **作る範囲**：
  - 候補生成：3戦略フル＋Step4（戦略別CFG）＋Best-of-N＋Step6 CLAP/PQ採点＋Step7（選別・配分）
  - 計装（三点セット）：①観測ログ ②スコア ③**人間採用ラベル**の捕捉（Step8）
  - UI：試聴＋採用が押せる程度
- **完了条件**：1セッション＝「構造化データ＋3戦略プロンプト＋各候補スコア＋採用したのはどれ」が**永続化**される（複数候補から耳で選ぶ体験が成立）。
- **範囲外**：本格的な層A（最低限のエラー処理のみ）／層C分析／パーソナライズ／GPU最適化。
- **対応／注記**：観測・評価設計 §13「MVP」＝この三点セット。本フェーズは Phase 1 の鎖の上に、それと候補生成（3戦略＋Best-of-N）を載せたもの。**最も重い段階**（必要なら「候補生成」と「計装」に分割可）。

### Phase 3 — 層A 検証ゲート（頑健化）

- **問い**：
  - パイプラインは荒い/曖昧な入力でも壊れないか？
  - ゴミを自信ありげに出さないか？
- **作る範囲**：Step2 スキーマ検証 → Step5 音声 liveness → Step3 トレーサビリティ → Step7 abstain ゲート。
- **完了条件**：変な入力でクラッシュせず、リトライ/修復/正直な abstain が効く（妥当性失敗＝層A と 品質不足＝abstain を**別フィールド**でログ）。
- **範囲外**：層C分析／パーソナライズ／最適化。
- **対応**：§13「次」。Phase 2 で“最低限の頑健性”は入れるが、ここで本格化。

### Phase 4 — 層C オフライン分析【本丸 ＝ ループを閉じる】

- **問い**：
  - 蓄積ログから、生成アルゴリズムを**定量的に**改善できるか？
  - proxy（CLAP/PQ）は人間採用と相関するか（proxy の妥当性）？
- **作る範囲**：
  - スコア vs 採用の**相関監視**
  - 戦略別採用率
  - **反実仮想リプレイ**（保存済み構造化データでプロンプトビルダーを作り直して比較）
- **完了条件**：ログを見て「ここを直す」を決め → テンプレ/パラメータ/重みを変え → **採用率で効果を測れる**（＝**外ループが1周回る**）。
- **意義**：ここで初めて「改善が回るアプリ」になる。**プロトタイプのゴール**。
- **対応**：§13「その後」。

### Phase 5 — GPU最適化／エンジン差し替え（プロトタイプ後）

- **問い**：生成アルゴリズムを変えずに速くできるか？
- **作る範囲**：生成エンジン抽象化の裏で diffusers 直叩き → ComfyUI 連携 or 自前最適化に差し替え（dev §2.2 後期）。
- **完了条件**：速度・GPU効率の改善（**アルゴリズム本体は不変**）。
- **なぜ後**：philosophy「GPU最適化は後」。良い音のロジックが固まってから。

### Phase 6 — パーソナライズ Tier1（プロトタイプ後）

- **問い**：単一の既定値（Tier0）では好みが満たせない兆候が出たか？
- **作る範囲**：例ベースのプリセット（耳で選んだ実例→ラベル保存→「適用」）。加算的探索（既定候補＋個人候補。観測・評価設計 §10.3）。
- **完了条件**：[FF-D008](./decisions.md) の昇格条件（音種別で好みが割れる／同種プリセットの反復作成 等）を満たしてから着手。
- **なぜ後**：Tier0 の土台が安定し、手動グローバルチューニングが頭打ちの証拠が出てから（FF-D008）。

- Phase 2 が重いので**さらに分割**するか（候補生成 / 計装 で2分割など）。
- 本書と §13 の**統合 or 役割分担**（§13 は評価系の段階に絞り、本書が全体計画、という分担が自然か）。
- Phase 0 のモデル比較で**どのモデルを候補にするか**（Stable Audio Open 他）。
- 各フェーズの Issue 化（[dev-workflow.md](./dev-workflow.md) の運用に乗せる）。
