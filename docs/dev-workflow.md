# 開発の進め方ルール（Issue・ラベル・決定ログ）

> このドキュメントは FoleyForge の開発における「進め方の約束事」を定めます。
> 決めたことの記録は [decisions.md](./decisions.md) を、開発の全体像・方針は [foley-forge-dev.md](./foley-forge-dev.md) を参照してください。

ガチガチには縛りません。普段は意識せず、判断に迷ったときだけ見るための、ゆるい約束事です。
このルール自体、運用してみて合わなければ変えてかまいません（変更は decisions.md に記録する）。

---

## 1. 情報の3レイヤー

開発に関する情報は、性質ごとに3つに分けて管理します。重複させないことで、二重管理とドリフト（不整合）を防ぎます。

| レイヤー | 置き場 | 役割 | 性質 |
|---------|--------|------|------|
| 全体像・方針 | `foley-forge-dev.md` | アプリの設計思想・処理フロー | 安定（肥大化させない） |
| 未決（追う） | GitHub Issues | これから決める／作るもの。1対1で起票 | 状態が変わる・クローズされる |
| 決定（残す） | `decisions.md` | 決めた事と理由の要約。俯瞰用 | 追記のみ・上書き禁止 |

GitHub Issues はクローズしても検索（`is:closed`）で残りますが、「決定だけを一覧で俯瞰する」用途には向きません。そのため、決定の要約は `decisions.md` に集約します。

> この3層とは別に、**整理済みの調査は `research/`（topic 別）**、**phase 別の生ノートは `docs/phases/`（§5）** に置く。生ノート（探索ログ）は確定したら3層／research へ**昇格**させる供給源で、それ自体は「真実」ではない。

## 2. ラベルのグループ（枠）

GitHub のラベルにグループ機能はありません。`グループ:値` という命名規約で、擬似的にグループとして見せます（一覧で同種が固まって見え、`label:グループ:値` でグループ単位の検索ができる）。

このドキュメントでは**グループ（枠）だけ**を定めます。**具体的なラベル値は定めません**（後述の理由）。

| グループ | 意味 | 必須か |
|---------|------|--------|
| `type:` | その Issue が「決めるもの／作るもの／調べるもの」のどれか | **必須**（1枚） |
| `phase:` | どの開発工程か（design / coding / test） | **必須**（1枚） |
| `area:` | アプリのどの部分に関わるか | 任意（0〜複数可） |
| `priority:` | 着手の優先順位（high / mid / low） | 任意 |
| `status:` | 特記事項（横断確認用）。普段は付けない | 任意 |

> `phase:` は「作業の工程」を表す。[prototype-roadmap.md](./prototype-roadmap.md) の Phase 0〜6（時間軸の開発段階。§5 参照）や `tta_local_web_architecture.md` の Phase 1〜6 のような時間軸のフェーズとは別物なので**混ぜない**こと。また、着手の優先順位は phase とは別概念。優先順位を表したくなった場合は phase に詰め込まず、別グループ（例: `priority:`）の追加を検討する。

## 3. ラベルの追加・削除・命名ルール

具体的なラベル値（`area:step2-llm` など）は、ここでは固定しません。**理由: 設計の進行で構成が変わりうるため**（例: Step 2 の位置付けが変われば、その値ラベルも変わる）。揮発しうる「値」をルールに焼き付けると、ルール自体が陳腐化します。

そこで、値そのものではなく「値をどう扱うか」を定めます。

### 命名

- 必ず `グループ:値` の形式にする（既存グループ `type` / `phase` / `area` / `priority` / `status` のいずれか）。
- 値は短く、内容が分かるものにする。

### 追加

- **値の追加は気軽に行ってよい**（例: 新しい領域が出たら `area:◯◯` を足す）。
- **新しいグループ（`type/phase/area/priority/status` 以外の `◯◯:`）の追加は慎重に**。一度立ち止まり、本当に既存グループで表現できないか考える。グループの乱立が、ラベル体系が崩れる最大の原因。

### 削除・改名

- 使われなくなった値ラベルは削除してよい。ただし、その値が付いていた **クローズ済み Issue から履歴が失われる**点に注意（過去を追えなくする変更なので、実害がないか確認してから）。
- 改名より「新ラベル追加 + 旧ラベル付け替え」のほうが履歴が追いやすい。

### 色

- 視認性のため、**比較できない（種別の）グループは、グループ内で色を揃える**。`type:`（決定/作業/調査）と `phase:`（design/coding/test）は優劣ではなく区分なので、それぞれ同色にする（例: `type:` 系は緑、`phase:` 系は青）。
- **比較できる（順序のある）グループは、段階が見えるよう色を変えてよい**。`priority:` は high=赤・mid=黄・low=灰 のように重要度のグラデーションで示す。

## 4. Issue 運用

Issue は「未決を追う」レイヤー。**open = まだ決まっていない（追う）／ closed = 決着（完了 or 不要）** が基本。未決の一覧は `is:open` で見る（タイプで絞るなら `is:open label:type:decision` など）。

### 起票（追加）

- **1つの未決事項につき 1 Issue（1対1）**。
- 起票はテンプレ（`decision` / `task` / `research`）から行う（`type:` ラベルが自動で付く）。
- 立てる前に既存 Issue を検索し、**重複していないか確認**する。
- 必須ラベル（`type:` と `phase:`）を必ず1枚ずつ付ける。`area:` / `priority:` / `status:` は任意。
- `priority:` は腐りやすい（主観が入り、放置すると全部 high 化する）。**付けたいものにだけ付ける**運用とし、全 Issue への付与は強制しない。`label:priority:high` で「今やるべきもの」だけ拾えれば十分。

### クローズ

クローズの分かれ目は「**まだ考える必要があるか**」の一点。後で考えるべきもの（見送り）は**閉じずに open のまま**置く（`is:open` に残しておけば見失わない）。決着したものだけ閉じる。GitHub のクローズ理由を使い分ける:

- **Completed（完了）** … やり切ったとき。締め方は `type:` ごとに異なる:
  - `type:decision` … `decisions.md` に1行残し、その行の**「関連 Issue」列に Issue 番号**を入れてからクローズ。
  - `type:task` … 「完了の定義」を満たしたらクローズ。PR から `Closes #<番号>` で紐づける（記録はコード／PR。`decisions.md` には書かない）。
  - `type:research` … 成果（`research/` への文書化、または判断材料）を残してクローズ。決定が要るなら `type:decision` の Issue に引き継ぐ。
- **Not planned（不要・重複・誤り）** … もう追わないとき。**理由をクローズコメントに1行**残す（重複は `Duplicate of #<番号>`）。`decisions.md` には書かない。

### 削除しない

Issue は**原則削除しない**。役目を終えたものはクローズで残す。削除は破壊的で、検索（`is:closed`）から消え、決定ログや他 Issue からのリンクが切れ、Issue 番号が欠番になる——「クローズ済み＝歴史」を自ら壊すことになる。不要・重複・誤りも、消さずに Not planned でクローズする。

### 後戻り（決定の見直し）

設計・実装を進める中で、クローズ済みの決定を再検討することは起こりうる。その場合:

- 元 Issue は**触らない**（クローズのまま＝歴史）。
- **新しい Issue を立て**、本文で元 Issue / 決定 ID にリンクする。
- `decisions.md` では、古い決定を `Superseded`（置き換え）にして**新エントリを追記**する（**上書きはしない**）。
- 単に未完了でクローズしてしまっただけなら、その Issue を **reopen** する。

## 5. phase の進め方（単一リポジトリ・タグ／ブランチ運用）

開発は [prototype-roadmap.md](./prototype-roadmap.md) の **Phase 0〜6**（時間軸の開発段階）に沿って進める。ここでの「phase」は §2 の `phase:` ラベル（design/coding/test の作業工程）とは**別物**。

**単一リポジトリ・1つのコードベースで進める（[FF-D011](./decisions.md)）。** phase は独立した成果物ではなく“積層”（Phase N は N−1 を拡張する）なので、**phase ごとにディレクトリや repo を分けない**。「成果が混ざらないように」は、コード分割ではなく **git の履歴・タグ・ブランチ**で実現する。

| 道具 | 役割 | 必須か |
|---|---|---|
| **`main`** | 常に「最新の動く状態」（最新 phase まで統合済み） | — |
| **タグ** | phase 完了時に打つ（例 `phase2-done`）。その時点を `git checkout` で再現でき、**各 phase の成果が混ざらず保存**される | **必須** |
| **ブランチ** | その phase の作業で main を壊したくない／実験したいときに切る。**完了条件を満たしたら main へマージして消す**（使い捨て） | 任意 |
| **GitHub Milestone** | phase ＝ マイルストーンとして Issue をグルーピング | 任意 |

### 基本の流れ

1. （任意）`phase-N` ブランチを切って開発。main を壊さない自信があれば main 直コミットでも可。
2. その phase の**完了条件**（roadmap 参照）を満たす。
3. ブランチを使ったら main へマージ。
4. **main に完了タグを打つ**（`git tag phaseN-done` → `git push --tags`）。
5. 次の phase へ。

> **やり過ぎない**：phase ごとに*永続的に並行する*ブランチを残すと、phase 別ディレクトリと同じ分岐地獄になる。永続するのは `main` ＋ タグだけ、ブランチは使い捨て。
> **生成物・ログ**：outputs やログが phase 間で混ざる懸念は、**実行・セッションごとに分ける**（ログにセッションID／`src/outputs` は gitignore）で解決。コード分割とは別問題。

### phase ノート（探索ログ）

各 phase で**調べたこと・分かったこと・実測・没案**は、`docs/phases/phaseN/` に**雑多に**貯める（形式自由）。詳細は [docs/phases/README.md](./phases/README.md)。

- ここは**生ログ（ジャーナル）であって真実ではない**。確定したら**昇格**させる：決定→`decisions.md`／設計変更→正典docs／再利用知見→`research/`。
- きれいに構造化したくなったら、それは「昇格」の合図。`phaseN/` 自体は雑多なままでよい。
- **正典docs（dev / obs-eval / decisions / dev-workflow / roadmap）は phase で割らない**（横断・進化する単一の真実）。phase 別に分けるのは生ノートだけ。
